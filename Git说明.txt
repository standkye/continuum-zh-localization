Git 版本管理说明
================

为什么建这个仓库
  这个项目干的是「字节级就地补丁」——直接改 DLL 里的字符串。
  改坏一次，AE 要么装不上、要么一用就崩，肉眼很难看出是第几步改坏的。
  有了 git，任何一步都能 diff / 回滚。

------------------------------------------------------------------
【每天最常用的三条】

  1. 看现在改了什么
       git status
       git diff                    # 看文本改动

  2. 做完一步就存一个快照
       git add -A
       git commit -m "第 11 批：补 xxx 译名"

  3. 改坏了，退回上一个快照
       git restore <文件或目录>      # 只还原指定文件
       git reset --hard HEAD        # ⚠️ 全部丢弃重来（未提交的改动会没）

------------------------------------------------------------------
【推荐的提交节奏】

  每一「批」翻完就提交一次，别攒着。这个项目的批次顺序天然就是安全的：

    ① 手写译名完成        -> 提交（词典 json）
    ② 跑完 checkN.py 自检 -> 提交（确认没有超容）
    ③ 跑完 fix4_dll.py    -> 提交（patches 落地）
    ④ 四件套验收通过      -> 提交（accept4 / overlap / enum / load）
    ⑤ 打包 + 装机成功     -> 提交（二进制快照，会 +240MB）

  这样任何一步出问题，`git log` 一翻、`git restore` 一下就回到上一个已知好状态。

------------------------------------------------------------------
【回滚示例】

  想知道装出来的 DLL 是哪一版：
      git log --oneline -- "Continuum 汉化组件 v19.0.0/BCCPlus.dll"

  想拿到上一版的 DLL：
      git show HEAD~1:"Continuum 汉化组件 v19.0.0/BCCPlus.dll" > BCCPlus_prev.dll

  想整批退回第 2 次提交时的样子（危险，会丢之后的改动）：
      git reset --hard <commit-id>

------------------------------------------------------------------
【几条硬规矩，别改】

  1. .gitattributes 里的 `* -text` 和仓库里的 core.autocrlf=false
     —— 这是刻意的。本项目靠「读回字节 == 写进去的字节」来保证没改坏，
        只要 git 偷偷做一次 CRLF/LF 转换，回读校验就会失败。
        别删那行，也别开 autocrlf。

  2. 6 支引擎 DLL 和安装器 exe 走 Git LFS。
     ⚠️ 前提：新环境（或别人电脑）上必须先 `git lfs install` + `git lfs pull`，
        否则 checkout 出来的 DLL 只是一个 133 字节的文本指针，AE 直接加载失败。
     装完 git 后验证方法：看 DLL 文件开头两个字节是不是 "MZ"
       xxd -l 2 "Continuum 汉化组件 v19.0.0/BCCPlus.dll"   # 应输出 MZ
     或者看文件大小，正常是几十 MB，不是 133 字节。

  3. 每提交一版二进制，.git/lfs 大约 +240MB。
     攒太多版会撑大仓库，磁盘紧张时可以：
       git lfs prune            # 清掉当前版本用不到的旧 LFS 对象
